# Архитектура: тип установки, профиль, драйверы

## Уровни сборки прошивки

```
ris400p.yaml (объект)          имя, сеть, калибровка, уставки — главнее всех
 ├─ boards/kc868_a8.yaml        плата: I2C, PCF8574, реле K1–K8, входы X1–X8 (без ролей)
 ├─ packages/core/*.yaml        ядро: цикл, защиты, журнал, интерфейс, сеть, время
 └─ profiles/salda_ris400p.yaml профиль: тип установки + драйверы + параметры + роли реле/входов
      ├─ packages/sensors/*.yaml   датчики (контракт ниже)
      └─ packages/drivers/*.yaml   драйверы оборудования
```

Порядок пакетов в файле объекта важен: плата → ядро → профиль. Более поздний пакет
переопределяет `substitutions` раньших, а `substitutions` файла объекта — главнее всех.

## Логика (C++, `firmware/include/vent/`)

Вся логика — заголовки без зависимостей от ESPHome. Они же собираются на компьютере
для тестов (`tests/`) и симуляции (`sim/`). ESPHome подключает каталог целиком,
поэтому каждый драйвер, включая заглушки, компилируется и в прошивке.

| Файл | Что |
|---|---|
| `hal.h` | Каналы: `DigitalOut`, `AnalogOut`, `SignalIn` (норма с учётом NC/NO), `AnalogIn`, `AlarmSink` |
| `esphome_hal.h` | Обёртки сущностей ESPHome в каналы — единственный файл, знающий про ESPHome |
| `system.h` | `VentSystem`: тип установки, проверка профиля, общие защиты, вызов драйверов |
| `sequencer.h` | Пуск/останов вентиляторов через `FanDriver`/`DamperDriver` |
| `alarms.h` | Общая таблица аварий, ручной/авто сброс, журнал |
| `control_math.h` | ПИ с anti-windup, гистерезис |
| `sensor_diag.h` | Диагностика резистивных датчиков в делителе |
| `<семейство>.h` | Интерфейс семейства + общая заглушка `<Семейство>Stub` |
| `<семейство>_<тип>.h` | Драйвер конкретного типа |

### Тип установки

`unit_type` в профиле: `SUPPLY` (приточная), `SUPPLY_EXHAUST` (приточно-вытяжная),
`EXHAUST` (вытяжная). Система проверяет, что набор драйверов подходит к типу, и по типу
решает, какие датчики обязательны:

| | приток | вытяжка | t_outdoor, t_supply | t_exhaust | t_extract |
|---|---|---|---|---|---|
| SUPPLY | обязателен | нет | обязательны | — | — |
| SUPPLY_EXHAUST | обязателен | обязательна | обязательны | если рекуператор требует | предупреждение |
| EXHAUST | нет | обязательна | — | — | предупреждение |

Охлаждение (режимы зима/лето) — отдельный драйвер к любому типу с притоком:
выключатель «Нагрев (зима)» / «Охлаждение (лето)».

### Проверка профиля

Если драйвер не задан, когда он нужен, не реализован (заглушка) или не подходит к типу
установки, срабатывает авария «Ошибка конфигурации» с точным текстом: установка не пускается,
выходы не трогаются, «норма» снята. Описание профиля пишется в лог при загрузке и в сущность
«profile Профиль установки». Проверено тестом `tests/test_vent_profiles.cpp` на каждой заглушке.

### Распределение ответственности

| Кто | Отвечает за |
|---|---|
| Система | режим, пожар, внешний стоп, датчики, перегрев притока, поток, фильтры, связь с платой, удержание продувки, «нагрев не управляется» → охлаждение, журнал, «норма»/«работа» |
| Вентилятор | ступень → выходы (реле/0–10 В/Modbus), пауза при смене, свои аварии (тахо, ток, ПЧ) |
| Нагреватель | регулирование, свои термостаты, «нехватка мощности», «тепло без команды»; нужен ли поток; разрешён ли пуск (прогрев водяного) |
| Рекуператор | защита от обмерзания (может менять скорости), преднагрев/байпас/ротор |
| Заслонка | открыть/закрыть, «открыта» по времени или концевику, авария привода |
| Охлаждение | регулирование, свои защиты (ККБ, дренаж) |

### Датчики (YAML, `packages/sensors/`)

Датчик температуры — пакет, который создаёт сущности по контракту:

| Сущность | Смысл |
|---|---|
| `${sensor_id}` | температура, °C; **NAN, если датчик недостоверен** |
| `${sensor_id}_fault` | binary_sensor «неисправность» (ON и при старте, пока данных нет) |
| `${sensor_id}_status_text` | норма / нет данных / обрыв / КЗ / вне диапазона / … |

Роль датчика (t_outdoor, t_supply, …) задаётся в профиле: `t_supply_sensor: t_supply`.
Отсутствующий датчик — `sens_absent`.

| Тип | Статус |
|---|---|
| NTC в делителе на ADS1115 (ратиометрия) — 10k B 3380/3435/3950, 20k, 1.8k | **реализован** (`ntc_ads1115.yaml`; тип — `ntc_r25`, `ntc_b_constant`) |
| NTC на АЦП ESP32 с подтяжкой платы | **реализован** (`ntc_esp32_adc.yaml`) |
| PT100, PT1000, Ni1000, KTY81/84 | план: пакет по тому же контракту (делитель/мост + формула типа) |
| DS18B20 | план: компонент `dallas_temp` + контракт |
| Активные 0–10 В / 4–20 мА, Modbus | план |

## Как добавить новый тип оборудования

1. `include/vent/<семейство>_<тип>.h` — класс, наследующий интерфейс семейства
   (`FanDriver`, `HeaterDriver`, …). Работать только через каналы `hal.h`.
   Новые аварии — коды в конец перечисления `alarms.h` (порядок не менять: маска во флеше).
2. `packages/drivers/<семейство>_<тип>.yaml` — объявить выходы/параметры, в `on_boot`
   (список, `priority: -50`) создать драйвер и зарегистрировать:
   `vent::vent_system().set_<роль>(new vent::<Класс>(vent::esph::out(id(...)), ...))`.
3. Подключить пакет в профиле вместо старого.
4. Тест в `tests/` на подделках каналов (`tests/salda_profile.h`, пространство `vent::fake`).
